# Installation and operation

## Configure your services

Use Python 3.11 or later, a PostgreSQL database with PostGIS enabled, and a writable GeoServer REST endpoint.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[postgis]"
Copy-Item .env.example .env
```

Edit `.env`: `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `GEOSERVER_URL`, `GEOSERVER_USER`, and `GEOSERVER_PASSWORD`. Supply database and workspace with each request; schema defaults to `public`. Process environment variables override `.env`; `--env-file` selects another file. Optional `GEOSERVER_PGHOST` supports a different database address from GeoServer, and `PGSSLMODE` selects PostgreSQL TLS mode. Never commit credentials.

On the original development PC, `scripts/start-native-geoserver.ps1` starts the locally installed service. Its ignored `.runtime` directory is not distributed. Other hosts must install or connect to their own services.

## Collect and publish

Provide an exact WGS84 GeoJSON polygon or multipolygon for the requested area:

```powershell
.\run.ps1 run --polygon area.geojson --category bank --sources openstreetmap --contact YOUR_OPERATOR_EMAIL --use internal --database YOUR_DATABASE --workspace YOUR_WORKSPACE --out output/banks
```

Normal CLI/API runs publish the database layer, register a styled GeoServer layer, and verify the result. Optional `--schema` and `--layer` select the destination. Missing publication inputs produce `needs_input`. Independent datasets should use separate schemas or layer names.

For natural-language requests, use `--intent "banks in Jeddah" --place-catalog places.geojson` instead of `--polygon` and `--category`. Arabic intent is supported. The supplied catalog must contain correctly named WGS84 polygon boundaries. Alternatively configure an approved `--place-provider provider.json`. Ambiguous place matches require clarification. A `--bbox` selects the rectangle itself, not an administrative city boundary.

## Sources and geometry

`sources.json` declares endpoints, licenses, attribution, permitted uses, coverage, and transport policies. The included OSM configuration permits internal use; redistribution or commercial use requires an operator-reviewed source configuration. Supply a real operator contact for live HTTP requests. Robots checks, endpoint rate limits and bounded retries are applied before processing.

Included live sources use `latest_available`: older available data can be processed with its timestamp and freshness state disclosed. This does not guarantee that no newer data exists elsewhere. An older response cannot replace a newer saved snapshot. Timeouts do not silently fall back to cached data. `--freshness-policy strict` enforces the configured age limit.

`--snapshot-from PATH` selects one integrity-checked historical capture explicitly. Share the durable snapshot state between workers handling the same source/query; do not reset it to bypass downgrade protection.

Source point coordinates are preserved. Missing coordinates are queued for review rather than fabricated. `--allow-source-centers` explicitly permits footprint-derived way/relation centers with provenance and capped confidence. Licensed `--geocode-catalog` or `--geocode-provider` can resolve address-only records; derived coordinates remain marked and ambiguous results stay in review.

Provider configuration contains `name`, `endpoint`, `license`, `attribution`, `allowed_uses`, `commercial_use`, and `rate_limit_per_second`. The generic public Nominatim endpoint is not accepted as a built-in collection/geocoding provider.

## Published attributes

The database record table has an integer `id` generated by a serial sequence as its primary key. The public PostGIS view and GeoServer layer expose `id`; internal `stable_id` is retained only for reconciliation, updates and replay. IDs survive updates and reactivation of a previously removed record. Sequence values need not be consecutive.

Required canonical fields remain even when their source values are missing. Optional columns appear when at least one record supplies a meaningful value. Provenance and geometry/name confidence remain available; generated names and derived coordinates are explicitly identified. Complete audit fields remain in the backing record table and captured artifacts.

## Incremental runs, replay and verification

```powershell
.\run.ps1 run --polygon area.geojson --category bank --sources openstreetmap --contact YOUR_OPERATOR_EMAIL --previous output/banks/records.json --database YOUR_DATABASE --workspace YOUR_WORKSPACE --out output/banks-refresh
.\run.ps1 replay output/banks-refresh
.\run.ps1 verify-local --database YOUR_DATABASE --workspace YOUR_WORKSPACE --layer poi_bank --out output/banks-refresh
```

`changes.json` records additions, updates, removals, unchanged records and field-level changes. Captures and provenance support deterministic offline replay without network access or an LLM. `verify-local` checks PostGIS records, EPSG:4326 geometry, source coordinates, WFS fields, WMS rendering, styling and attribution.

Use `--no-publish` (API: `"publish": false`) for an explicit file-only preview. An existing preview can be published with `publish --out PATH --database DATABASE --workspace WORKSPACE`, then checked with `verify-local`.

## Containers and evaluation

```powershell
docker build -t poi-harvester .
docker run --rm --entrypoint python poi-harvester -m unittest discover -s tests -v
docker run --rm -v "$($PWD.Path)/output:/app/output" poi-harvester evaluate --out output/container-evaluation
```

Windows users with Docker Desktop can run `scripts/run-local-demo.ps1`. It starts isolated PostGIS/GeoServer services, stores random local credentials in ignored `.env.container`, and publishes explicitly labeled invented demo POIs. `scripts/stop-local.ps1` stops those services without deleting their data. This is a publication demonstration, not real POI evidence.

```powershell
.\run.ps1 evaluate --ratings fixtures/arabic_name_review_human_ratings.json --out output/evaluation
```

Add `--local-services --database DATABASE --schema TEST_SCHEMA --workspace TEST_WORKSPACE` to include service checks. Use isolated targets for synthetic evaluation fixtures. Generated evaluation and readiness reports go under ignored `output/`; they distinguish local evidence from official certification.
